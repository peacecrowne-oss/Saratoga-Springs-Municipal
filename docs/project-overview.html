Architecture

One Node.js 24 server and one SQLite database file on a City machine, with no third-party packages. Staff use pages in a browser; residents use a public portal with no sign-in. Every outside system is reached with a timeout and capped retries.

Engineering rules this build follows

  • Audit trail first. A change and its audit record are saved in one transaction. If the audit record can't be written, the action doesn't happen.
  • Every side effect is idempotent. Repeated submissions, retried messages and re-run migrations never duplicate anything.
  • Every external call has a timeout and capped retries. Only failures that may clear on their own are retried.
  • No error is swallowed. Failures are explained to the person, recorded, and sent to the server log.
  • Simulated means labelled. Data from a stand-in says SIMULATED on screen and in the data.

What's built

Each story, with its acceptance criteria and the failure paths it handles. A stakeholder version with screenshots is in the Word briefing (not in the repository).

STORY-000 · Command Center Verified · 57 pts

The project dashboard at GitHub Pages, reading .colaberry/plan.json, progress.json and manifest.json by their data contract, so the numbers it shows are the real ones.

STORY-001 · Deploy the initial system Verified · 73 pts

npm run deploy proves the system works in five steps: open the database, listen, pass the health check, read the asset records as a signed-in service, and write a system.deploy audit entry. Any failure after step 1 is audited as system.deploy_failed, and the failed step is named. The server refuses to listen beyond this machine without a TLS proxy.

STORY-002 · Integrate with ESRI ArcGIS Verified · 73 pts SIMULATED ArcGIS

The ESRI REST client (generateToken, paged query, applyEdits) and npm run gis-sync. Fields the system owns are pushed; fields and geometry owned by GIS are pulled; disagreements are flagged as mismatches. Handles outages, timeouts, refused credentials (with one token refresh), schema changes and rejected edits.

STORY-004 · Asset lifecycle management Verified · 73 pts

The Asset Management page: inventory search and filters; statuses planned → active ↔ maintenance → retired (retired is final); condition readings kept as history, where the latest observation counts; maintenance tasks; and discrepancy flags such as "critical but still active", which are never auto-fixed. It refuses impossible moves, stale edits and future-dated readings, and names every invalid field.

STORY-005 · Synchronize asset data with GIS Verified · 73 pts SIMULATED ArcGIS

Every pushed feature is read back and checked, and spatial problems are recorded with a verification time. --reconcile compares the whole layer. The sync log can be reviewed with npm run gis-log (add -- --errors for failures only) and through /api/gis/log.

STORY-006 · Code enforcement permits Verified · 73 pts

The Permitting page and two new roles, permit clerk and code enforcement officer. Numbers take the form CE-YYYY-NNNN. Approval needs a reason and both compliance checks (code section verified, site inspected). Nobody decides their own application, decisions are final, and a decision that can't be audited doesn't happen. Applicants' personal details stay out of the audit trail and the queue.

STORY-007 · Public portal Verified · 73 pts SIMULATED email

Residents apply at /portal without an account and receive a private link, of which only the hash is stored. Through the link they book or move the site inspection: a weekday, from tomorrow, up to 60 days ahead, with 8 inspections a day. Confirmations are queued with the action, sent with a timeout and capped retries, retried in the background, and never sent twice. Wrong links and floods from one address are blocked and logged.

STORY-012 · Secure sign-in Verified · 73 pts

A password (scrypt hash) and then a 6-digit authenticator code (TOTP). Sessions are HttpOnly SameSite=Strict cookies that end after 30 minutes idle or 8 hours. Lockouts apply per user and address, per user, and per address. A session used from another address or browser is ended as a suspected hijack. Every attempt is recorded before the answer goes out. Accounts are managed with npm run auth-admin. PII handling is in docs/SECURITY.md.

STORY-010 · Caselle billing Verified · 73 pts SIMULATED Caselle

GET /api/billing/accounts/:number for billing managers, and the headless job npm run caselle -- account <n>. Money is whole cents, and a balance must equal what the open bills owe or the data is refused. A credentials error is refused once and not retried. Every request is logged with the user and the time before any data goes out.

STORY-013 · Cityworks migration Verified · 73 pts SIMULATED export

npm run migrate -- <export> brings in permits, licences, service requests, inspections and work orders, with fees, people, GIS links and attachments, and writes a reconciliation report. The /history page shows the records as read-only. See Migration.

STORY-011 · Final testing and acceptance Submitted · 2 of 3

An end-to-end smoke test (13 checks: a real deployment, every role signed in with real codes, every module), the Testing dashboard at /testing with 14 acceptance scenarios, and npm run test-report, which writes docs/TEST-REPORT.md. The report is COMPLETE only when every section has real content. Its verdict is READY only when all tests pass and acceptance holds: every scenario run, all passing, no critical issue open. Acceptance currently stands at 5 of 14 scenarios, all passing.

Interface additions

Staff dashboards have a City-blue heading bar, a calm background, a Back button in the heading, and a "Back to the list" button on asset, permit and Cityworks record panels.

Cityworks migration

An export is a folder: cityworks.db (the SQL export in SQLite), manifest.json (row counts and version), attachments/, and gis-features.json (an ArcGIS feature snapshot).

  • Preflight: the run is refused, writing nothing, if a table is missing, if the data doesn't match the manifest, if the schema has drifted (no known name for a required column), or if the attachments exceed the quota, the free disk space or the per-file limit.
  • Files: attachments are copied into storage named by SHA-256, verified after copying, stored once and skipped on a rerun.
  • Records: written in one transaction. The historical tables open for writing only inside it; database triggers refuse every other change.
  • Reconcile: counts are compared independently, every stored file is re-hashed, and every GIS link is checked against the snapshot. A link that is missing, ambiguous, in an unknown layer, or to an unknown record is listed for a person, who resolves it through --resolutions.
  • Verdict: TRUSTED only when every count matches, no link is orphaned and nothing is unresolved.
Scale test: 200,000 simulated attachments and 2,000 records came out TRUSTED. All files were stored and hash-verified, with 0 orphaned links. The first run took 34 minutes on a Windows laptop; a rerun took 3 minutes and copied nothing.

The by-department cutover plan is in docs/CUTOVER.md. Recommended option: full history, read-only, with each department closing out its open items before cutover, rehearsed on two dry runs. If departments need more time, phase it by department.

Audit trail

audit_event records who did what to which record, when, and the record before and after. Database triggers refuse any update or deletion. record() writes the event or throws, so a caller can't carry on unlogged.

Audited actions include deployments; sign-in attempts, alerts and session events; asset changes and refusals; GIS pushes, pulls, mismatches and failures; permit submissions, views, decisions and refusals; portal views, bookings, refusals and blocks; notifications sent, failed and given up; billing lookups, failures and denials; Cityworks views, downloads and refused writes; migration runs and refusals; acceptance results; and test reports.

How to run it

Node.js 24 is the only requirement; there's nothing to install.

npm run auth-admin -- add-user <name> --role it_administrator   # shows a password and authenticator key once
npm run standin            # SIMULATED Tyler (port 4100)
npm run caselle-standin    # SIMULATED Caselle (port 4300)
npm run arcgis-standin     # SIMULATED ArcGIS (port 4200)
npm run deploy             # the system, at http://127.0.0.1:3000/login

npm run sample-export -- data/sample-export && npm run migrate -- data/sample-export
npm run gis-sync           # needs ARCGIS_LAYER_URL etc.; the stand-in prints them
npm run caselle -- account SIM-1001
npm test                   # all automated tests
npm run test-report        # suite + smoke test + acceptance → docs/TEST-REPORT.md

Settings

These come from the environment or a local .env that is never committed: HOST, PORT, DB_PATH, TRUST_PROXY, AUTH_SECRET_KEY, PUBLIC_BASE_URL, TYLER_BASE_URL, CASELLE_BASE_URL, CASELLE_API_KEY, ARCGIS_LAYER_URL, ARCGIS_TOKEN_URL, ARCGIS_USERNAME, ARCGIS_PASSWORD, ATTACHMENTS_DIR and MIGRATION_MAX_ATTACHMENT_BYTES.
