Municipal Asset Management and Permitting Software Solution

A system for managing municipal assets and permitting processes that integrates with the City's existing systems and gives staff and the public secure, easy-to-use access.

Architecture

Node.js 24 with no third-party dependencies: the built-in node:http, node:sqlite and node:test modules, and global fetch. One SQLite database holds the records and the append-only audit trail. Integrations are isolated behind client modules, each with timeouts and capped retries.

Engineering rules this build follows

  • Walking skeleton first: the thinnest end-to-end path, including the audit trail, came before any features.
  • Every external call has an explicit timeout and capped retries. Only failures that may clear on their own are retried: no answer, timeout, HTTP 5xx and 429.
  • Every side effect is idempotent. A repeated asset create, a repeated update and a repeated sync all write nothing new, and GIS edits are never blindly retried.
  • No swallowed errors. Failures carry a kind, surface to the caller and are audited where possible.
  • No secrets in the repository. Credentials come from the environment or a git-ignored .env. The only password in the code belongs to the SIMULATED stand-in.

STORY-000 · Command Center Verified · 57 pts

A 9-tab static site at the repository root (live on GitHub Pages). It reads the plan and progress at runtime from .colaberry/plan.json, progress.json and manifest.json, so it is never hand-copied.

  • Tabs: Overview, Outcomes, Users, Guardrails, Systems, Project (Gantt of dated releases), Agents, Knowledge (keyword chat over the project's notes) and Data Model.

Proven by tests/command-center.test.mjs, which crawls every tab and link with real data, sample data and no data, and checks that deleting a story removes it from the page.

STORY-001 · Deploy Initial System with Core Functionalities Verified · 73 pts

  • Given the system is ready for deployment, when the deployment process is initiated, then the system should be operational with core functionalities.
  • Given the system is deployed, when a core functionality is accessed, then it should perform as expected.
  • Trust: Given the deployment process, when it completes, then an audit log entry is created with deployment details.

"Core functionalities", as agreed with the product owner: a health check, plus asset records (create and read, with each create audited and idempotent by asset tag). Updating assets was added later, in STORY-002.

How deployment works (npm run deploy, server/deploy.js):

1. open the database and create its tables   → core_init_failed
2. listen on host:port                         → network
3. GET /api/health until it answers ok         → unreachable / unhealthy
4. GET /api/assets as the deployer             → core_check_failed
5. write a system.deploy audit event           → audit_failed
   (version, commit, host, database, every check, duration)

A deployment does not count until step 5 is written. Any failure after step 1 stops the server and is audited as system.deploy_failed.

Failure paths handled

Story's failure pathWhat happens
Deployment fails due to network issuesPort already taken: DEPLOYMENT FAILED (network): EADDRINUSE. A health check that never answers is retried 3 times and then fails. Both are audited.
Core functionality does not initialiseThe database won't open, so nothing starts. The message says plainly that no audit entry could be written.
Audit log entry is not createdThe server is stopped and the deployment is reported as failed: "a deployment that is not on the record does not count".

Real run: Deployed 0.1.0 (f8b397a…) in 275 ms · Checks: database ok, listen ok, health ok, assets ok · Audit entry bcce3ff7… (system.deploy).

STORY-002 · Integrate with ESRI ArcGIS Enterprise Verified · 73 pts SIMULATED ArcGIS

  • Given the system is connected to ESRI ArcGIS, when asset data is updated, then GIS layers should reflect these updates.
  • Given a GIS field value is changed, when I check the system, then it should show the updated value.
  • Trust: Ensure all GIS transactions are logged for audit.

A headless GIS Sync Job (npm run gis-sync, or --watch every GIS_SYNC_INTERVAL_S seconds; server/gis-sync.js). Each run:

1. check the layer has every field the sync needs   → schema_mismatch
2. pull features edited since the last run, page by page
   · store GIS-owned fields + geometry on the asset   → gis.pull
   · GIS edit to a field we own                       → gis.mismatch (our value pushed back)
   · feature whose tag matches no asset               → gis.mismatch (unknown_asset)
3. push every asset changed since its last push       → gis.push / gis.push_failed
   · an unlinked asset is looked up by tag first, so nothing duplicates
4. summary                                            → gis.sync_run  (or gis.sync_failed)

Field ownership (agreed)

Owned by our system → pushedOwned by GIS → pulled
ASSET_TAG, NAME, ASSET_TYPE, STATUS, LOCATION_DESCGeometry and every other attribute (for example MATERIAL, DIAMETER_IN, INSTALL_YEAR)

Failure paths handled

Story's failure pathWhat happens
REST endpoint authentication failureBad sign-in or rejected token: the run stops, nothing changes, it exits 1 and is audited. An expired token is refreshed once.
Data mismatch between system and GISOwned-field edits, unknown features and missing layer fields are all detected and audited.
Network latency issuesTimeouts and capped retries. applyEdits is never retried, so it can't duplicate; the next run catches up.

Groundwork, claiming no story · Tyler budget integration SIMULATED Tyler

This was built for a story in an earlier version of the plan, which the platform later replaced. Audit trail

The trust guarantee this system makes: nothing happens unlogged. audit_event is append-only, enforced by two database triggers that abort any UPDATE or DELETE. audit.record() either writes the event or throws AuditWriteError, so no code path can carry on after an action went unlogged. Changes and their audit events are written in a single transaction.

How to run it

Needs Node.js 24 or later. There is nothing to install: no npm install, because there are no dependencies.

# tests
npm test

# deploy and run the system (then open http://127.0.0.1:3000/system)
npm run deploy

# SIMULATED ArcGIS, in another terminal; it prints the four ARCGIS_* settings to use
npm run arcgis-standin

# GIS sync, once (exits 1 on failure) or continuously
npm run gis-sync
npm run gis-sync -- --watch

# SIMULATED Tyler, for the budget page
npm run standin
